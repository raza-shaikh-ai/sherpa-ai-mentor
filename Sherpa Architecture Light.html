System architecture

Sherpa indexes a repository, then explains it: an architecture map, a tech stack tree, guided tours, a Repo City built from commit history, and answers that cite the exact files and commits they came from. The same app runs in the browser, on macOS and Windows, on iOS and Android, and from a CLI. The backend runs in one AWS region, with the app on EC2 and data in RDS on the same private network.

Three requests, end to end

The paths a judge sees in a demo, in the order the services handle them.

Index a repository

  1. Paste a URL, upload a zip, or pick one of your public GitHub repos.
  2. The API checks the URL against the SSRF guard, then shallow-clones the default branch.
  3. Files are parsed and chunked. Titan Text Embeddings v2 turns each chunk into a 1024-number vector.
  4. Chunks, vectors and file stats are written to RDS in Postgres.
  5. Commit history is fetched the first time it is needed and cached per indexed commit.

Ask Sherpa a question

  1. The question arrives with the session JWT, and the daily quota is checked.
  2. Hybrid retrieval scores keywords while pgvector finds similar chunks, then merges both.
  3. Questions about history also get the matching commits and exact last-changed dates from git.
  4. Qwen3-Coder writes the answer. Kimi K2.5, then DeepSeek V3.2, take over if a call fails.
  5. Any markdown link the model invents becomes a proper citation or plain text. Each [file] and [commit] citation is then checked; unknown ones are dropped, and clicking one opens the code viewer, never a new tab.

Sign in with GitHub

  1. The API signs a state token that expires in 10 minutes.
  2. The browser goes to GitHub's authorize page and returns to /auth/github/callback.
  3. The page checks the state, then sends the code to the API.
  4. The API exchanges the code and reads the profile and verified emails.
  5. The account is matched by GitHub id, then by verified email, or created. A session JWT is issued.
